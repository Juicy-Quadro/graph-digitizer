# 云图提取 · Cloud Map

**版本**：v1.3.0 引入
**适用对象**：等值线填色图（contour map）、热力图（heat map）、任何「颜色代表数值」的图

---

## 为什么单开一个工作区

折线图的数据模型是「系列 → 点序列」：一条曲线、一串坐标。云图的数据模型是「数值场」：一整幅图上每一点都有个数值，而且这个数值不来自坐标，而来自**颜色**。

把两者塞进同一张表会有三个坏处：

1. 颜色 → 数值的映射会丢失（表格里只剩坐标，看不出这个点是什么值）
2. 撤销栈会被数值场撑爆（网格是 `Float32Array`，JSON 序列化后是几十万个数字）
3. 导出格式对不上：折线图要的是「X, Y」，云图要的是「网格矩阵」

所以云图有独立的面板、独立的标定和独立的导出，产出的文件可以直接进 Excel / Origin / Python。

## 原理

### 第一步：读出色标的颜色

在色标框内逐行扫描。每一行取**出现次数最多的量化颜色**作为这一行的代表色（不用均值，因为刻度线、文字框会让均值偏掉）。每行还要占据该行 20% 以上的像素，否则这一行不算色带。

得到一串 `(位置 t, 颜色)`，其中 `t` 从色标低端 0 到高端 1。

### 第二步：建立颜色 → 数值映射

刻度值给的是「位置 → 数值」的若干锚点（`anchors`）。色标上每一行的颜色按它自己的位置插值得到一个数值，于是每个颜色都有了一个数值。

然后把颜色空间量化成 `32 × 32 × 32` 的查找表，每个格子记录**最近的那条色带**。查询时：

- 查表得到候选色带
- 再用**精确的** redmean 色差算一次真实距离
- 距离超过容差（默认 36）就判定「这个颜色不在色标上」→ 该像素不属于云图

最后这一步是关键：坐标轴、文字、白色背景都在色标上找不到对应颜色，会被自动排除，不会污染数据。

标度支持 `线性` 和 `对数`（对数时在 log 空间插值，两端值必须都大于 0）。

### 第三步：提取数值场

在指定范围内按 `Grid step` 逐格查表，命中的格子写下数值，没命中的留空（导出时是空单元格，不是 0）。

## AI 读刻度是怎么工作的

视觉模型（M3）看不到像素级位置，所以流程是：

1. 渲染层把色标**横向**扩出去一倍多（只扩一边，保留纵向范围），连同旁边的刻度文字一起裁下来
2. 裁剪图 + 图像尺寸送给模型，模型回答 `{ "ticks": [{ "label", "value", "position" }] }`
3. `position` 是裁剪图里的像素坐标，渲染层换算成色标上的 `t`

**实测**（MiniMax-M3，160×300 的合成色标，标签 100 / 75 / 50 / 25 / 0）：

| 标签 | 模型读到的值 | 位置误差 |
|---|---|---|
| 100 | 100 | 0 px |
| 75 | 75 | 3 px |
| 50 | 50 | 3 px |
| 25 | 25 | 4 px |
| 0 | *(未读出)* | — |

260 px 高的色标上误差约 3 px，相当于满量程的 1.2%。所以**模型给的是初值，数字可以随手改**——刻度表里每个数值都是可编辑的输入框。模型读不出来的标签会留空，等你填。

模型读不出某个标签时，它会返回 `value: null`，那一行会提示「还需要填写数值」。

## 两种标定方式的关系

刻度值和坐标标定是**两套独立的东西**：

| | 坐标标定 | 色标标定 |
|---|---|---|
| 回答的问题 | 这个像素在哪 | 这个颜色是多少 |
| 作用 | 网格的 X/Y 坐标 | 网格的数值 Z |
| 四点标定 | 是 | 否 |
| 色标刻度 | 否 | 是 |

导出时两个可以自由组合：

- 没做坐标标定 → 网格是像素坐标
- 做了坐标标定 + 勾选「按标定坐标导出」→ 网格是逻辑坐标

## 精度

### 在合成等值线图上

颜色还原的数值平均误差 **0.37**，最差 1.4（约两个色带宽度）。这是颜色量化方法的固有精度——色带越宽越准。

### 在真实论文图上

从 arXiv 论文 **2601.00342**（*Solving nonlinear subsonic compressible flow in infinite domain via multi-stage neural networks*）的源码包里取出原图，裁出四个带色标的面板做回归：

| 面板 | 色标 | 刻度标签 | 颜色读数误差 |
|---|---|---|---|
| `uv_a1` | jet | 5 / 0 / −5（×10⁻¹） | **0.77%** 量程 |
| `uv_a2` | jet | 5 / 0 / −5（×10⁻¹） | **0.77%** 量程 |
| `uv_a3` | 发散（RdBu） | 1 / 0（×10⁻⁶） | **1.72%** 量程 |
| `uv_b1` | jet | −6 / −7（×10⁻²） | **0.73%** 量程 |

误差最大的位置都在色标的**平坦端**（jet 最深的红、RdBu 最深的蓝）——那一段颜色几乎不变，颜色本身就不能唯一确定数值，这是方法的固有歧义，不是缺陷。

夹具可以随时重建：

```bash
python tools/fetch_paper_figures.py
node tools/run-tests.js
```

### 真实论文图逼出来的两个修复

1. **查找表太粗**。原来用 32×32×32 的颜色查找表，一个格子是 8 个色阶——而一条 1800 像素长的色标上，8 个色阶相当于 50 多个像素，颜色直接认错了带，数值偏 2%。改成**精确最近邻搜索**（按颜色分桶后逐圈向外找），误差降到 0.8%。
2. **刻度标签常常盖不满整条色标**。真实论文里标签只标了中间几段，两端没有标签。原实现把锚点之外的值**压平成端点值**，等于把一段云图的值全报成同一个数。改成**沿最近两个锚点的直线外推**，标签没覆盖的部分才不会被抹平。

## 已知限制

- **色带宽度决定精度**。色带越窄，颜色量化误差越大。合成图上平均误差 0.37（色带宽 0.625），最差 1.4——这是方法本身的上限，不是 bug。
- **渐变色标（viridis 之类）比彩虹色标准**，因为彩虹色标在拐点附近颜色变化剧烈。
- **JPEG 压缩过的图**会有色块边界模糊，容差不够时会漏掉边界像素。
- **离散分档色标**（只有几个固定色块）也可以用，但每一档内部只能给出同一个值——这是数据本身的性质。
- **目前只导出栅格**，没有从数值场反推等值线。
