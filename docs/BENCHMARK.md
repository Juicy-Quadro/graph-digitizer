# 论文图 Benchmark · 真实图片上的能力评测

**目的**：回答一个具体问题——**视觉模型在真实论文图上，到底比经典算法强多少、弱多少。**

之前的所有验证都建立在「为算法量身做的」合成图上。合成图能验证数学，但回答不了「面对真实论文图会怎样」。这个 benchmark 用几百张真实论文图来回答。

---

## 图从哪来

从 arXiv **论文源码包**里取，不是从渲染页截图——所以拿到的是作者原始的高分辨率图。

```bash
python tools/bench_fetch.py --count 400 --papers 140
```

- 分类覆盖 `astro-ph.IM/GA`、`cs.LG/CV`、`physics.flu-dyn`、`math.OC`、`eess.IV`、`q-bio.PE`、`cond-mat.stat-mech`、`physics.optics`、`stat.ML`、`nlin.CD`、`hep-ex`、`astro-ph.SR`、`cs.DB`
- 时间范围：2024-01 之后
- 图片统一缩到最长边 1400 px，存成 JPEG
- **默认 400 张图、140 篇论文**，实际产出 **400 张图**（论文里图多的会贡献多张）

论文地址、标题、分类都记在 `testdata/bench/papers.json` 里，每张图都能追溯到原文。

## 怎么评

### 经典算法当基准线

`tools/bench-reference.js` 对每一张图跑一遍**普通算法**（和应用里完全同一套代码）：

- 自动找出图里最突出的颜色 → 生成掩膜 → 取最大连通块 → 沿它追踪
- 找出色标：一条窄的、颜色饱和的竖条
- 找出色标旁的刻度标签：暗色文字块的位置

结果写在 `testdata/bench/manifest.json`。

### 400 张图上的实际情况

| | 数量 | 占比 |
|---|---|---|
| 能检测到色标 | **189** | 47% |
| 色标旁有 ≥2 个刻度标签 | **139** | 35% |
| 经典追踪器能追出一条曲线 | **1** | 0.25% |

**最后这一行是本次评测最重要的发现**：经典追踪器在真实论文图上几乎完全失效——真实图有坐标轴、网格、文字、多条曲线，掩膜会把它们全捞进来，追踪立刻跑偏。

所以曲线任务**没有可用的真值**，只能用无标注指标；色标任务则有可靠的真值（标签位置由程序测出）。

## 两个任务，两套指标

### 任务一：读色标刻度（`--task bar`）

模型看到的是**色标及其两侧**的裁剪图（横向扩出去两倍多，把刻度数字带上），它回答每个刻度的文字、数字和它在色标上的位置。

| 指标 | 含义 | 真值来源 |
|---|---|---|
| `positionError` | 模型报的位置与印刷标签的实际位置差多少像素 | 程序测出的标签位置 |
| `residual` | 模型读的数字对不对 | **直线残差**：色标上的数值对位置应该是直线，某个数字读错就会偏离这条直线 |
| `residualPrinted` | 把模型给的数字放到程序找到的位置上，残差多少 | 同上，但用程序的位置 |
| `ok` / `ticks` | 有没有给出可用的回答 | — |

`residual` 是这个任务里最漂亮的指标：它不需要人工标注任何数字。刻度标签通常是等距或按已知规律分布的，模型读错一个数字，那一点就会明显偏离直线。

`positionError` 同样重要——它量的是模型**不擅长**的那件事，而程序擅长，所以产品里的分工就是按这个来的。

### 任务二：读曲线（`--task curve`）

没有真值，所以只看两件**不需要标注**的事：

| 指标 | 含义 |
|---|---|
| `onStructure` | 模型给的点，有多少真的落在图上画出来的线上（看该点邻域的颜色有没有突变） |
| `coherence` | 这些点是不是连成一条连续的路径（相邻点跳得很远说明模型在乱指） |
| `deviation` | 有经典参考时（极少数图），模型点离参考曲线多远、覆盖了参考的多少 |

## 它已经查出来的十一件事

### 一、经典追踪器在真实论文图上基本失效

400 张图里，经典追踪器只追出 **1 条**曲线。真实图有坐标轴、网格、文字、多条曲线，掩膜把它们全捞进来，追踪走出曲线。

**结论**：在真实论文图上，自动追踪这条路需要模型来补，而不是靠参数。

### 二、模型读出的曲线点，94%–100% 真的落在图上画的线上

在第一批有答案的图上，模型返回的点里，落在「有画线结构」的位置上的比例中位数 **93.9%**、p90 **100%**。这不是说它找得准（没有真值），而是说它**没有在瞎指**——它看的是图里的线。

### 三、模型一开始读不出真实图上的刻度标签——这是应用的真 bug

第一批测试里，模型对每张图都回答「没有刻度」。它自己的推理说得很清楚：

> "ticks right labels **clipped by image right edge**"
> "text cut"
> "labels shown: -0.5, -1.0, -2.0..."（这是**猜的**）

原因有两个：

1. **裁剪图把数字切掉了**——窗口只按色标宽度往外扩，标签的文字没被框进去
2. **色标是一条 1:8 的细条**，模型接口会把长边缩到 1000 多像素，刻度数字就只剩几个像素高

修法（已进应用）：

- 窗口**跟着文字走到头**（扫出整段里最后一个暗像素，而不是第一个）
- 裁剪图**放大到长边 1400 像素**
- **不旋转色标**——旁边的数字和色标是同一个排版方向，转了图字也跟着转

修完之后，同一张图上模型读出了 `-2.950`、`-3.694`，还自己把刻度的像素位置和间距算了出来。

### 四、模型读数字很准，但报位置不准——所以两边分工

修好裁剪之后，真实色标上的读数是这样的：

| 图 | 读到的刻度数 | 位置平均偏差 | 数字的直线残差 |
|---|---|---|---|
| Charge_Density_concentration | 5 | 24 px | **0.01%** |
| Charge_Density_depth | 5 | 26 px | **0.11%** |
| Charge_density_pH | 5 | 28 px | **0.11%** |
| Charge_Density_BMI | 6 | 63 px | **0.06%** |

**残差**是这么算的：色标上的数值对位置本来应该是直线，模型把某个数字读错，那一点就会明显偏离这条直线。0.01%–0.11% 意味着**它读的数字基本全对**。

但**位置偏了 24–63 像素**。这在真实图上是致命的——按位置插值，几十像素就是十几个数值单位的误差。

于是分工改了（已进应用）：

- **程序找位置**：色标旁的刻度文字是暗色块，程序能精确找到每一个（`findTickLabels`）
- **模型只给数字**：它擅长读数，不擅长报位置
- 两边**按顺序就近配对**，配不上的才用模型自己给的位置

这样模型的强项被用上，弱项被绕开了。

### 五、曲线请求的 token 预算不够，答案被切断

曲线任务里有一半的图模型没给出 JSON。它的理由写在回复里：它**先思考再回答**，而一张有几条曲线的图，答案本身就要很多 token。预算只有 16000，于是回复在 JSON 开始之前就被切断了。

改成 32000，并在提示词里要求「每条曲线最多六十个点」。

重测那张原本失败的图：现在返回 **3 条曲线、33 个点**，而且**每个点都落在图上画的线上**。

### 六、裁剪图放大过，模型报的位置却没有除回去——最大的一个 bug

裁剪图在送给模型之前会**放大到长边 1400 像素**（不然刻度数字只有几个像素高，看不清）。模型是在**放大后的图**上读位置的，而应用却把它当成**原图上的位置**。

差多少？放大 4.7 倍就是差 4.7 倍。

修法（已进应用）：`tick.position / crop.scale`。

修完之后的实测（色标任务，同一批图）：

| 指标 | 修之前 | 修之后 |
|---|---|---|
| 位置偏差中位数 | 84.9 px | **1.5 px** |
| 位置偏差 p90 | 155 px | **13 px** |

这是整个 benchmark 里**对应用影响最大的一个发现**：模型其实把位置报得很准，是应用自己把坐标算错了。

### 七、程序找刻度标签时，会把旁边的图例当成刻度

应用里找刻度标签的办法是「取离色标最近的那一列文字，再按行分块」。这个办法有两个毛病：

1. 色标旁边只要有**别的文字更近**（图例、坐标轴标题），找到的就是那一列，真刻度全丢了
2. 旁边**一个孤零零的脏点**就能把整列刻度带偏，全军覆没

实测（400 张真实图）：最差的那个刻度标签，程序和参考答案差 **129 像素**；换掉策略之后降到 **35 像素**，参考标签的 **87.5%** 都能对上。

新办法（已进应用）：不再挑某一列，而是**把窗口里所有带文字的行都投影出来**，一个都不丢。哪一行是真刻度，后面由「哪个数字属于它」来定——模型报的位置就是线索，最近的那个文字行就是它。

这正好是 benchmark 的价值：参考实现在这里也是错的，是把它和应用放在一起比才暴露出来的。

### 八、水平色标的刻度标签根本找不到，色带编号也从错的端点开始

界面里色标可以选水平方向。水平的时候：

- **刻度标签在色标的上下方**，而找标签的代码只看左右两侧 → 一个都找不到
- **裁剪窗口只按左右扩**，标签在下面就被切掉了
- 更糟的是 `scanBar` 把「避开边框和刻度线」的那 25% 收窄**用在了色标的长度方向上**，于是色带是从色标的 25% 处开始编号的，和用户填的刻度值对不上——**数值是错的**

修法（已进应用）：水平色标的收窄改到厚度方向上，编号走满整条长度；标签在上下方找；窗口跟着上下方的文字走。

### 九、benchmark 自己量错了：它用的是参考实现的标签位置

`residualPrinted` 这个指标——「把模型给的数字放到程序找到的位置上，残差多少」——一直用**参考实现**（`bench-vision.js`）找到的标签位置。

而参考实现的窗口是**从色标右侧 20 像素开始**的。真实图上色标的刻度标签就贴在色标边上（离色标不到 20 像素），于是参考实现**根本没看见真刻度**，它找到的是坐标轴的数字或者图例。

所以那个「28.98%」量的是参考实现的毛病，不是模型的。

现在这个任务改成用**应用自己的**标签代码（`GD.ColorBar.findTickLabels`），配对方式也和应用一致。

顺带修的：benchmark 声称「中断可以接着跑」，但那个「已测过」的集合建了从来没用过——其实每次都从头重跑。

### 十、刻度位置被旁边竖排的标题带偏了

真实图上，色标旁边常常还有一个**竖着印的标题**（比如 `ρ_ab (mol/cm³)`）。它和刻度数字占着同样的行，于是「按行投影」把两者并成了一块，而这一块的中点不是任何一个数字的位置——旁边的刻度被带偏了 10–20 像素。

三种量法在同一张真实图上的结果：

| 位置从哪来 | 数字的直线残差 |
|---|---|
| 模型自己报的 | 0.119% |
| 程序按行投影找的（含竖排标题） | **2.85%** |
| 程序按行投影找的（剔除异常高的块）+ 只在很近时才采用 | **0.054%** |

修法（已进应用）：

- 一行文字是**矮的**。远高于其他块的那一块，是竖排的标题，不是刻度 → 剔除
- 程序的位置**只在离模型给的位置很近时（色标长度的 1%）**才采用。模型读位置其实很准，而旁边可能有根本不是数字的文字块，取它的中点反而会把数字放错地方

### 十一、两个纯工具的 bug

- **「中断可以接着跑」从来没生效**：`done` 集合建了从来没被用过，每次都从头重跑
- **后台跑会弹错误窗**：管道一断，`console.log` 抛 EPIPE，没人接，整个进程倒下，Electron 弹窗。顺带发现新版 node 里 `'%d' % 5` 已经是 `NaN`，要改用 `console.log` 的占位符

## 成本

一次曲线提取约 60–90 秒（模型要输出上百个点），一次色标读数约 40–70 秒。

- 189 张图读色标：约 2 小时
- 400 张图读曲线：约 8 小时

所以评测是**分任务、分批次**跑的，不是��把 400 张图 × 2 个任务一次性烧完。

## 结论怎么读

这个 benchmark 回答的是**「模型能不能替代人工读图」**，不是「模型是不是万能」。具体地：

- 读色标：只要位置误差和直线残差够小，模型读出的刻度就可以直接用；读不准的地方人工改一改就行（界面里每个数字都是可编辑的）
- 读曲线：真实论文图上经典算法会失败，如果模型能稳定给出「点落在线上 + 路径连续」的答案，那它是**互补**而不是替代——两条路都留着，用户挑
